# Известные ограничения и риски

## Основные риски

| Приоритет | Риск / расхождение | Где видно | Последствие |
|---|---|---|---|
| Высокий | Входящие сообщения пишутся в `messages_log` без маскирования; база содержит связь MAX ID/ФИО | `monitor/storage.py`, `db/schema.sql` | SQLite-файл может содержать персональные данные и требует ограничения доступа/хранения |
| Высокий | HR и head-HR уведомления «успешны» на уровне сценария, если chat ID пуст, но фактически только логируются | `monitor/bot/max_adapter.py`, `.env.example` | Тикеты и red flags могут остаться без реального HR получателя |
| Средний | Offer-коды прямо хранятся в mock JSON/таблице сотрудников; реальный выпуск, срок действия и одноразовость не заданы | `mock_hris.json`, `monitor/db.py`, `monitor/storage.py` | Это только демо-привязка, не production-аутентификация |
| Средний | `flows.py` очень крупный и смешивает маршрутизацию, бизнес-логику и прямые SQL-запросы | `monitor/flows.py` | Изменения FSM/опросов могут иметь неожиданные побочные эффекты |
| Средний | `TIME_SCALE` масштабирует timeline offsets, но не все временные механики и не полный календарь рабочих часов | `monitor/timeline.py`, `monitor/flows.py` | Ускоренная демо-временная шкала может расходиться с ожиданиями по напоминаниям |
| Средний | Параллельные запуски приложения не координируются распределённой очередью; scheduler и polling живут в одном процессе | `main.py`, `monitor/timeline.py` | Несколько реплик могут одновременно выбрать одну pending-задачу |
| Средний | В репозитории есть две реализации MAX, два scheduler пути и несколько старых AI helpers; их нельзя считать активными по одному наличию кода | `monitor/bot/delivery.py`, `monitor/pipeline/scheduler.py`, `monitor/agents/`, `monitor/alerts/` | Разработчик может отлаживать неиспользуемый путь или подключить несовместимый старый schema |
| Низкий | В `main.py` используется APScheduler interval polling раз в 15 секунд, а не выделенная CRON/queue архитектура | `main.py` | Большие объёмы данных потребуют другого планирования/масштабирования |

## ТЗ: намерение и фактическая реализация

| В ТЗ / ожидании | Сейчас в коде |
|---|---|
| PostgreSQL и pgvector предложены как рекомендуемый production stack | SQLite и JSON-based RAG index |
| RAG и AI ответы входят в целевой прототип | `ENABLE_RAG=false` по умолчанию; неизвестные вопросы передаются HR; legacy NLU не подключён |
| HRIS интеграция не входит в прототип | Используется только `mock_hris.json` |
| MAX integration — один adapter | Активная точка входа соблюдает это; legacy `delivery.py` реализует отдельный прямой HTTP путь, который сейчас не вызывается |
| Таймлайн должен сдвигать сообщения на рабочее утро при выходе за рабочие дни/часы | `_shift_to_workday()` переносит выходные на понедельник; не реализует полное правило рабочего времени |
| Необходимы персонализированные тексты и вложения по площадкам | Часть вложений и площадочных материалов пока заменена TODO, ряд этапов пропускается/ограничен |
| Аналитика не должна содержать прямые идентификаторы | CSV используют `employee_id` псевдоним и маскирование текстовых полей; исходная БД всё ещё хранит PII и MAX ID |

## Демо-заглушки и неясности

- Значения HR chat IDs, manager IDs и разрешённые администраторы должны быть настроены; без них часть уведомлений только логируется.
- В `OPEN_QUESTIONS.md` перечислены утверждение binding flow, SLA, тексты «ВЫ», материалы, направления HR, роли команд и BI-потребности.
- `BINDING_METHOD` есть в конфигурации, но активный сценарий ищет только offer-код; альтернативные binding стратегии не реализованы.
- `DEMO_MODE` присутствует в настройках, но отдельного переключения сценариев через него в активном flow не видно.
- Отсутствующие фотографии, карты, презентации, книжные и иные файлы должны быть предоставлены заказчиком.
